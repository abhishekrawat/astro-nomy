## At a glance

**The opportunity:** Reduce the repeated interpretation between a design decision and its implementation.

**The approach:** Connect reusable components to their implementation, then use AI to assist with the surrounding work.

**The standard:** Include review and correction in any measurement of delivery speed.

This sample narrative develops the Code Connect, knowledge repository and content-pipeline work described on the About page. The workflow below is illustrative until replaced with actual project evidence.

## Find the bottleneck before choosing the tool

Handoff friction often appears in small, recurring questions. Which component is this? What happens in an empty state? Does this value come from a token? Which behaviour changes in Arabic?

A useful starting point is to observe where a team repeatedly reconstructs intent. That creates a concrete target for automation and a baseline against which to assess the result.

## Decision 01: Connect to existing components

The proposed workflow starts with the system the team already maintains: component names, variants, tokens and usage guidance. AI-assisted implementation needs that context to produce something that fits the product.

The portfolio illustration shows a sample appointment component alongside its implementation contract. It represents the relationship; it is not a screenshot of an internal tool.

## Decision 02: Keep judgment in the loop

| Stage | AI can assist with | Human responsibility |
| --- | --- | --- |
| Frame | Organising existing material | Define the problem and constraints |
| Build | Scaffolding and repetitive changes | Choose the interaction and architecture |
| Review | Finding inconsistencies and edge cases | Verify behaviour, accessibility and fit |
| Learn | Summarising recorded observations | Decide whether the change helped |

The review step belongs inside the workflow. A first draft that arrives quickly but requires extensive correction is not automatically a delivery improvement.

## Decision 03: Make the improvement reusable

A useful internal tool should be understandable by someone who did not build it. The handoff should include the input it expects, the result it produces and how to recover when it fails.

The same principle applies to a knowledge repository or content pipeline: make sources and review status visible, and provide a clear path back to a person.

## What I would measure

- Time from an agreed design to a reviewed, working implementation.
- Time spent correcting generated work, including regressions.
- Reuse of approved components and consistency across states.
- Whether colleagues can use the workflow independently.

Use comparable tasks and record the sample size. Include the costs of setup and maintenance rather than reporting only the best run.
