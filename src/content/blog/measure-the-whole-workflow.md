## Define where the clock stops

When comparing an AI-assisted workflow with an existing process, the finish line matters. A generated screen, a reviewed prototype and a production-ready change are different outcomes.

Choose the outcome before measuring. For a design-to-code experiment, that might mean an implementation that uses the approved components, handles the agreed states and passes the team’s review.

## Count correction as work

A useful record includes time spent explaining context, generating the change, checking it and correcting it. If the first draft saves an hour but creates an hour of additional review, that is part of the result.

The point is to find where the workflow helps. Repeated, well-specified changes may behave differently from novel interactions or work with poorly documented constraints.

## Compare like with like

Use a small set of comparable tasks and record what made them comparable. Include the inputs, the expected outcome and the reviewer’s acceptance criteria.

Then look beyond elapsed time. Did the result use existing components? Did another person understand it? Did the workflow introduce a new maintenance burden?

## Make the learning actionable

A strong experiment ends with a decision: keep this step, change the instructions, improve the source material or stop using the workflow for this class of task.

That learning is more valuable than an impressive number without a baseline. The goal is a repeatable improvement in how a team delivers.
